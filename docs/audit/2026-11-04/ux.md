# UX / copy / accessibility audit (update of 2026-10-16)

Scope: branch `field-build-oct23` (98 commits ahead of `main`) plus the uncommitted working tree (compass rework in `map_screen.dart`, estimated-layer silence samples in `coverage_map_detail_screen.dart` and `lib/services/estimate_samples.dart`, new app icon from `tool/icon_art.png`). Read-only code review of `lib/ui/**`, `lib/demo/**`, user-facing strings in `lib/services/**`, `ios/MeshActivity`, `ios/Runner/Info.plist`. The icon was previewed with `PREVIEW=/tmp/icon_preview.png tool/make_icon.py` and downscaled to 60 px. No simulator run this time; every finding below was checked in the code.

## Summary
- First-run is much better than on 10-16: a three-page welcome, a four-step Get started card, a Radio Setup intro with numbered steps, plain error and success rows, an End session confirmation and a Delete map dialog with counts. A new tester with two Meshtastic radios can now reach a recorded session without the website. The weak spots are two competing checklists (Live and Coverage) and Radio Setup's remaining jargon.
- Three HIGH issues. (1) The Pro paywall still appends "Coming soon." to every feature it doesn't list as shipped, and MeshCore and Guided tests are not on that list, so a user who taps a MeshCore radio is shown a paywall saying MeshCore is coming soon. (2) Radio Setup writes the mobile's key into the base's admin list without asking in the mobile-first flow; in the base flow the checkbox is on by default and doesn't say what it grants, that it may evict another admin key, or that "Put back" doesn't undo it. (3) The new `userMessage` helper swallows the carefully worded `StateError` refusals ("The base and the mobile must speak the same protocol", "That is the mobile radio itself, not the base") into "Something went wrong while setting up the radio (StateError)", while about 15 places still show raw `$e`, now including every guided-test screen.
- Terminology is the biggest MEDIUM theme: MeshCore users still meet "pings" in Settings, the Live Activity, the estimated-layer chip and the guided result. Meshtastic text mixes "Range preset", "Preset", "modem presets" and "range setting". Raw preset ids (`MEDIUM_FAST`, `MC_SF7_BW62.5_CR5`) still reach the lock screen Live Activity, the radio sheet and the Compare picker.
- The compass rework is sound (Apple Maps model) but the "heading up paused" state has no visible or spoken cue, so the map starts turning again after the resume timer with no warning. A pinch-zoom also pauses heading up.
- The new icon is on brand in energy but busy at 60 px: the sunset is cropped at the right edge, the dot ramp is red to green (the colour-blind problem the map already has), and the artwork's origin and licence are not recorded anywhere in the repo.
- Counts: 3 HIGH, 9 MEDIUM, 12 LOW. Of the 16 prior UX findings: 3 Fixed, 10 Partly fixed, 3 Still open.

## Findings

### [HIGH] Paywall says MeshCore and Guided tests are "Coming soon" although both ship
**Where** lib/ui/screens/pro_paywall_screen.dart:190-195 (`_shipped`), :224-230 (`'${_blurbs[f]!} Coming soon.'`); trigger lib/ui/widgets/connection_banner.dart:572-575; enum lib/services/pro_entitlement.dart:31-41.
**What** `_shipped` holds only `rigProfiles`, `rigComparison` and (when the backend URL is set) `aiAnalysis`. `meshCore` and `guidedTests` both work and are both gated, but render with the schedule icon and "Map and test MeshCore radios too. Coming soon." / "Guided test with three or four setups in one go (two are free). Coming soon." The MeshCore paywall opens exactly when a user taps a MeshCore radio in the connect list, under the bold line "MeshCore radios is a Pro feature." Four genuinely unbuilt features (placement advisor, PDF report, offline packs, iCloud) are still listed next to a buy button, which is what the 10-16 audit flagged under App Review 3.1.2.
**Why it matters** The one moment the paywall is most likely to convert, it tells the buyer the thing they want doesn't exist yet. Reviewers read the feature list literally.
**Fix** Add `ProFeature.meshCore` and `ProFeature.guidedTests` to `_shipped` (better: derive "shipped" from a `shipped` flag on the enum so a new feature can't be forgotten). Split the list into "Included" and "Planned", or drop the planned rows until they ship. Fix the grammar of the trigger line: "MeshCore radios need Pro." / "Guided tests with 3 or 4 setups need Pro."

### [HIGH] Remote-admin grant at the base: silent in one flow, under-explained in the other, not undone by "Put back"
**Where** lib/ui/screens/radio_setup_screen.dart:482-500 (mobile flow `_applyToBase`, no `allowRemoteChanges` argument), :83 (`_allowRemote = true`), :1212-1223 (checkbox, base flow only); lib/services/radio_profile_service.dart:507-536 (`allowRemoteChanges = true` default), :222; lib/data/radio/meshtastic/meshtastic_admin_keys.dart:28-34 (full list evicts the oldest key); lib/data/radio/meshtastic/meshtastic_radio.dart:1694-1705 (eviction only logged); lib/ui/widgets/radio_backups_section.dart:486-489 (backups list name, channels, LoRa, Range Test; no security config).
**What** When the phone is connected to the mobile and the user taps "Find base radio", the base is set up with the mobile's public key in `security.admin_key` with no checkbox and no mention in the confirm dialog (radio_setup_screen.dart:374-390 text says channels, preset, restart, backup). In the base flow the checkbox "Allow the mobile radio to change this base from a distance" is pre-ticked; its subtitle ("Needed for guided tests that change range settings. Only your own mobile radio's key.") doesn't say it grants full remote admin of the base. If the base already has three admin keys (a power user's own remote-admin phone or node), the oldest is silently replaced. "Put this radio back the way it was" restores from a backup that has no security config, so the grant stays.
**Why it matters** This is a security setting on the user's own hardware, often a roof node they also manage remotely. The power-user review's M4 trust point ("this app knocked my router off the mesh") applies doubly to "this app replaced my admin key".
**Fix** Show the same checkbox in the mobile flow, unticked by default (or ticked only after the user starts a plan that needs it). Reword: title "Let my mobile radio change this base over the air"; subtitle "Adds the mobile's key to the base's admin list, so guided tests can switch its range setting from a distance. You can remove it later in Radio Setup." When the list is full, ask before replacing ("The base already has 3 admin keys. Replace the oldest?"). Make "Put back" remove the key the app added (it knows it: `RadioRoles.remoteAdminMobileNode`) and say so in its dialog.

### [HIGH] Error text: friendly helper hides the useful messages; raw `$e` still in about 15 places
**Where** lib/utils/user_errors.dart:71-90; callers lib/ui/screens/radio_setup_screen.dart:462, lib/services/guided/plan_runner.dart:1008,1410,1442,1489. Raw sites: lib/ui/widgets/session_panel.dart:894; lib/ui/screens/settings_screen.dart:516; lib/ui/widgets/radio_backups_section.dart:119,334,349,407; lib/ui/widgets/export_dialog.dart:31; lib/ui/widgets/region_dialog.dart:64; lib/ui/widgets/terrain_profile_sheet.dart:139; lib/ui/widgets/connection_banner.dart:341,348,498; lib/ui/screens/coverage_map_list_screen.dart:79; lib/ui/screens/about_screen.dart:144; lib/ui/screens/guided/ask_screen.dart:229, plan_screen.dart:48,133, run_screen.dart:90,261, result_screen.dart:53.
**What** `userMessage` only passes a `StateError` through when it contains "rejected", "not ready" or "not connected". Every other refusal written for the user in the services falls to "Something went wrong while setting up the radio (StateError). Try again; if it keeps happening, send us the details from Settings → About." Examples that are lost: `RadioProfileService.sameProtocolMessage` (:88), "That is the mobile radio itself, not the base" (:399), "The mobile radio's public key isn't known yet; connect to it and try again" (:390), "The base radio is not known yet. Set it up in…" (:454), "The radio has no free channel slot for MeshTest" (meshcore_radio.dart:913), "The base's range setting is not known" (plan_runner.dart:1401). The MeshCore relay refusal does match "rejected" but is lower-cased by the helper, so the user reads "(relaying is not allowed on 915.000 mhz. a meshcore base can only relay on 433.000, 869.495, 918.000 mhz.)". Meanwhile the raw sites still print "Restore failed: Bad state: Connect to the radio first", "Failed: …", "Scan failed: PlatformException(…)", "That did not work: …", and the connect help appends "Details: <exception>" to every failure.
**Why it matters** The runtime type name is the jargon the helper was written to remove, and the real reason (wrong protocol, wrong radio) is the one thing the user needs to fix it.
**Fix** Introduce a `UserFacingError` (or reuse `SessionStartError`/`PlanError`) for every message written for people, throw it from the services instead of `StateError`, and let `userMessage` return its text verbatim. Keep `StateError` for programmer errors. Drop the `.toLowerCase()` on the "rejected" path (only lower-case enum-style tokens like `NOT_AUTHORIZED`). Route every `$e` site above through `userMessage(e, doing: …)`; put "Details" behind a "Copy details" action instead of inline.

### [MEDIUM] Two first-run checklists with different steps and different dismissal
**Where** lib/ui/screens/map_screen.dart:549-555 (`FirstRunCard` on Live); lib/ui/widgets/first_run_card.dart:56-58,87-95 (`first_run_dismissed`); lib/ui/widgets/get_started_card.dart:59-102 (Coverage, `onboarding_checklist_hidden_v1`); lib/ui/screens/about_screen.dart:211-212.
**What** Live shows a "Get started" card (connect only counts while connected now; "Radio Setup: put both radios on the private test channel"; "Start a session and walk"), and Coverage shows a second "GET STARTED · n/4" card with different logic (a radio ever connected counts) and different titles ("Run Radio Setup", "Record your first walk"). **Fix** Keep one checklist (the Get started card, which reads real state and is the one CLAUDE.md documents). Delete `FirstRunCard` or make it a one-line "Finish setup: step 2 of 4 →" pill on Live that opens the Coverage card, sharing `checklistHiddenProvider`.

### [MEDIUM] Estimated-layer chip: the new silence line is inaccurate in three ways
**Where** lib/ui/screens/coverage_map_detail_screen.dart:720-729 (chip), :897-904, :978-980 (terrain path uses received events only); lib/services/estimate_samples.dart:56-84.
**What** (a) The count `silent` includes ack events with no usable signal (relayed or implicit replies, estimate_samples.dart:66-73), so "12 unanswered pings" over-counts: some of those pings were answered. (b) In RSSI mode the silence sample is −130 dBm and the legend says "RSSI ≤ -120", but the chip still says "count as no margin". (c) With "Terrain-aware estimate" on, silence is dropped and the line disappears, so the stretch the tester complained about (TestFlight 2026-11-04, "why green between the base and the red?") turns green again with no explanation. On MeshCore the samples are link checks, not pings.
**Why it matters** The line exists to explain a visible change on the map; if it is wrong or vanishes the user can't trust either layer.
**Fix** Count timeouts and no-signal replies separately, or word it to cover both: "12 pings with no direct reply drawn as no signal". In RSSI mode: "… drawn as -130 dBm". On the terrain chip add "Uses received signals only; unanswered pings aren't drawn" (or feed `EstimateSamples` into the terrain path too). Use `probeNoun` for MeshCore.

### [MEDIUM] Compass: "heading up paused" is invisible, and pinch-zoom pauses it
**Where** lib/ui/screens/map_screen.dart:88-100 (twist turns it off), :136-197 (`_setHeadingWanted`, `_setFollow`, `_syncHeading`, `_onCompassTap`), :199-204 (`_compassTooltip`), :401-415 (`onPositionChanged` pauses on any gesture), :628-660 (locate and compass FABs).
**What** Three visible states exist: filled orange "Heading up · tap for north up", outlined and rotated "Tap for north up", outlined north "North up · tap to turn with you". The fourth, real state (heading wanted, paused by a pan) looks identical to "rotated by a twist", yet behaves differently: while recording, the map starts turning again on its own when the resume timer fires, and the locate button silently brings heading up back. `onPositionChanged(hasGesture: true)` fires for pinch-zoom too, so zooming in to read a dot drops follow and freezes the rotation. The north-up tooltip doesn't say that tapping also recentres and follows. VoiceOver hears the tooltip only, with no selected/toggled state.
**Why it matters** A map that rotates by itself after you stopped touching it reads as a bug in the field; zoom is the most common gesture on a walk.
**Fix** Show the paused state: outlined icon with an orange dot or ring and tooltip "Heading up paused · tap for north up"; give the locate button "Follow and turn with you" while heading up is wanted. Only drop follow on a pan (compare camera centre before and after, or check `MapEventMove` vs `MapEventDoubleTapZoom`/pinch). North-up tooltip: "North up · tap to follow and turn with you". Wrap the compass FAB in `Semantics(toggled: _headingActive, label: 'Heading up')`.

### [MEDIUM] Colour-only encodings: Live legend now off by default, guided check rows say "green"
**Where** lib/ui/screens/settings_screen.dart:227-232 ("Show colour key on the Live map … Off by default; the dot colours read on their own."); lib/utils/signal_color_mapper.dart:43-62 (red, yellow, green ramp unchanged); lib/ui/widgets/guided/check_list.dart:143-167 (`CheckDot`, a 12 px coloured square, blinking when busy); lib/ui/screens/guided/run_screen.dart:351-353 ("Fix the rows that are not green", "every row is green").

Respect `MediaQuery.disableAnimations` for the blink. Consider a colour-blind-safe ramp option (blue to yellow) in Display settings.

### [MEDIUM] New app icon: busy at small sizes, cropped sun, red-green dots, provenance unrecorded
**Where** tool/icon_art.png (1254 px RGB, no metadata besides an ICC profile); tool/make_icon.py:22-29,131-158 (`from_art`, `ART_TRIM = 0.02`); ios/Runner/Assets.xcassets/AppIcon.appiconset/* (regenerated, uncommitted); NOTICE (no icon entry).
**What** Previewed at 1024 and 60 px.

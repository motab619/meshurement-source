## Project Overview

**Meshurement** (formerly Mesh Analyzer): Flutter/Dart iOS app for GPS-mapped signal strength analysis of Meshtastic mesh networks. Personal proof-of-concept, iOS-only. Connects to Meshtastic nodes via BLE, logs signal data (SNR/RSSI) with GPS coordinates, and visualizes coverage on a map.

## Build & Development Commands

```bash
# Install dependencies
flutter pub get

# Generate drift database code (required after changing tables/queries)
flutter pub run build_runner build --delete-conflicting-outputs

# Run on connected iPhone (BLE doesn't work in simulators)
flutter run

# Run tests
flutter test

# Analyze code
flutter analyze
```

## Architecture

Three-layer unidirectional data flow:

1. **Data Layer**: `MeshRadio` interface (`lib/data/radio/`, protocol-neutral; `MeshtasticRadio` and `MeshCoreRadio` implement it, `SwitchableRadio` swaps between them by the picked radio's protocol), drift SQLite DB, Geolocator
2. **Service Layer**: `PacketProcessor`, `SessionManager`, `RangeTestDetector`, `ActiveProbeService`, `OutOfRangeMonitor`
3. **UI Layer**: Flutter widgets watching Riverpod `StreamProvider`s

**Key data flow**: `MeshRadio` packet/routing/nodeInfo streams → `PacketProcessor` (single subscriber, started once in `app.dart`) → DB writes + UI stream emission. Everything branches from PacketProcessor.

**State management**: Riverpod. All providers are defined in `lib/providers.dart`. `SharedPreferences` and `FlutterLocalNotificationsPlugin` are initialized in `main.dart` and injected via provider overrides.

**Database**: drift (SQLite) with code generation. Tables are in `lib/data/database/tables/all_tables.dart`, queries in `lib/data/database/app_database.dart`. Generated file: `app_database.g.dart`. After any table/query changes, re-run `build_runner`.

**Data model hierarchy**: CoverageMap → Sessions → PacketEvents. Nodes are referenced by PacketEvents and Sessions. PingCorrelations link TX/ACK packet event pairs for active probing.

## Key Conventions

- `print()` is used for dev logging (lint rule `avoid_print: false`)
- `prefer_const_constructors` and `prefer_const_declarations` are enforced
- Radio layer (`lib/data/radio/`): services and UI depend only on the abstract `MeshRadio` (`mesh_radio.dart`) and the neutral types in `radio_types.dart` / `radio_preset.dart` (`RadioDescriptor`, `RadioNode`, `ReceivedPacket`, `PingOutcome`, `TestProfile`, `RadioPreset`). `MeshtasticRadio` (`meshtastic/`) holds all protocol logic plus Meshtastic-only extras (`loraConfig`, `channels`, `sendAdmin`, `enterDemo`...); `MeshtasticPresets` maps protobuf modem presets to `RadioPreset`. `ble/BleTransport` (parameterized by service/characteristic UUIDs, reusable for MeshCore) and `ble/RadioScanner` are the only flutter_blue_plus code. Pings go through `MeshRadio.ping` (ACK matching and NAK/throttle classification happen in the radio; `ActiveProbeService` records the `PingOutcome`; the DB's `PingResult` row class is a different thing). Sessions store `protocol` (schema v5) next to `loraPreset`.
- Import rules: `flutter_blue_plus` only under `lib/data/radio/ble/`; `package:mesh_analyzer/proto` only under `lib/data/radio/meshtastic/`, `radio_backup_service.dart` and `demo/demo_seeder.dart` (and tests). Backups need `radio is MeshtasticRadio`; `AirtimeModel` works on `RadioPreset`.
- Meshtastic BLE transport, ported from the working coachella-mesh app (`~/develop/coachella-mesh/src/mesh/`): subscribe FromNum → write `ToRadio{wantConfigId: random}` → read FromRadio until empty until `configCompleteId` matches; drain on every FromNum notify; heartbeat 60 s; auto-reconnect with backoff (in `MeshtasticRadio`). Pairing PIN is left to the iOS system prompt.
- Protobufs are the upstream meshtastic/protobufs, vendored **unmodified** in `lib/proto/` (tag/commit in `lib/proto/UPSTREAM.md`, GPL-3.0 `LICENSE` beside them) with Dart generated by protoc + protoc_plugin 22.x (runtime `protobuf` ^4). Import as `package:mesh_analyzer/proto/meshtastic/<x>.pb.dart' as pb`. Never hand-edit; regenerate with `tool/gen_protos.sh`. `lib/proto/**` is excluded from analysis. (The old `meshtastic_flutter` package was dropped.) Since 2026-11-10 they are **v2.8.2** (were v2.7.26, which read a 2.8 radio's MEDIUM_TURBO/TINY_* as LONG_FAST): `MeshtasticPresets` has MEDIUM_TURBO (2.8+, left out of `presetsForRegion` when the radio's `firmwareVersion` is known to be < 2.8, so a 2.7 radio isn't offered a preset it would run as Long Fast; a 2.7 *base* during a remote change is caught by the rollback) and TINY_FAST/TINY_SLOW (ham 2 m regions), and the ham 1.25 m / 70 cm regions offer the narrow presets, all from firmware v2.8.2.d5f1619 `MeshRadio.h`/`RadioInterface.cpp`. `_dropUnknown` stays for values newer than the vendored protos.
- Port numbers: ROUTING_APP = 5, ADMIN_APP = 6, RANGE_TEST_APP = 66, TELEMETRY_APP = 67, TRACEROUTE_APP = 70.
- Pings are PRIVATE_APP DMs with want_ack (not text, so the base doesn't notify). The ping is recorded and registered in `_pendingPings` *before* sending. ACKs are matched by `Data.requestId` == packet id. ACK from the destination = `received`; from another node = `implicit`; NAK = `error:<Routing_Error name>`; no reply in 30 s = `timeout`, and so is a MAX_RETRANSMIT NAK from our own radio (it sent, retried and heard no ACK: what a deaf base actually produces, bench 2026-11-09; `AckStatus.noReplyReasons`/`isNoReply`, older rows say `error:MAX_RETRANSMIT` and the estimate layer and Field Report count them as misses). Starting pings first sends our NodeInfo (want_response) to the base so both know each other's PKI keys. Firmware 2.7.19+ refuses to DM a node whose key it lacks: a *local* `PKI_SEND_FAIL_PUBLIC_KEY` NAK from our own node, nothing goes on air (before 2.7.19 the DM went out channel-encrypted); `PKI_UNKNOWN_PUBKEY` is the *base's* NAK (~1 s round trip) when it can't decrypt ours. Both happen e.g. after a node list reset, so `MeshtasticContacts` (`radio_contacts_v1` pref) keeps our own radios' `User` records (own node saved on every connect, ping target saved when known, both saved in Radio Setup); `MeshtasticRadio.ensureContact` re-adds a missing key with `AdminMessage.add_contact` before pinging and on a PKI NAK, and Radio Setup gives each radio the other's key. Clear nodes list keeps (favourites) the Radio Setup base and every map's base.
- Radio Setup (`RadioProfileService`, Settings → Radio Setup) puts the mobile and base radios on a private channel "MeshTest" (32-byte key generated once, stored in SharedPreferences `test_channel_psk`) as the ONLY enabled channel, plus a chosen modem preset. **Never test on the public channel**: `SessionManager.startSession` refuses if `MeshRadio.onPublicChannel` (primary key ≤ 1 byte). Admin sequence over BLE (no session passkey): beginEdit → setChannel ×8 → setConfig(lora) → setConfig(device) → setModuleConfig(telemetry) → setModuleConfig(rangeTest) → commitEdit; the commit reboots the radio, so a lost ACK on commit counts as success. Base = beacon sender; mobile = receiver (both `role = CLIENT` and `rebroadcast_mode = LOCAL_ONLY`, mobile telemetry broadcast off; backups keep the original role and relaying for Restore). Roles are chosen, not inferred: Radio Setup asks whether the connected radio is the mobile or the base (base flow: set up the connected radio as base, then `switchToAndApplyMobile` moves the phone's connection to the mobile). `RadioRoles` (`lib/services/radio_roles.dart`, `radioRolesProvider`) remembers each role by node number (`base_node_num`, `mobile_node_num`) and Bluetooth id (learned on connect); the connect list tags radios, picking the base asks first, and the map pill/radio sheet show the role. Optional renaming (on by default) sets owner names "MeshTest Base"/BASE and "MeshTest Mobile"/MOBL in the same settings transaction; backups now include the owner (`User`) so Restore puts the old names back.
- Base beacon (schema v7, `docs/design/beacon-kinds.md`): firmware 2.8 compiles Range Test out (and 2.7.26 lacks it on classic ESP32), so the base runs a `BeaconKind`: `telemetry` (device telemetry broadcast; needs `device_telemetry_enabled` on 2.7.26 and 2.8) or `rangeTest` (`seq N`), never position (6 h floor on 2.8). `selectBeaconKind(MeshRadio.capabilities)` picks telemetry when `DeviceMetadata.excluded_modules` has the Range Test bit, firmware ≥ 2.8 or unknown firmware; else Range Test. `BeaconConfig.resolved` rounds telemetry intervals up to whole minutes (min 60 s): the firmware telemetry module only wakes every 60 s. `PacketProcessor` records base telemetry (0 hops) and Range Test as beacon samples (`packet_events.seq`, `source_kind`, `base_channel_util`; `sessions.beacon_kind`, `beacon_interval_sec`). `BeaconTracker` counts seq gaps, synthesises `telemetry_miss` rows from timing (hidden from maps, counts and every export except the full CSV) and flags the beacon as off when the base is heard but no beacon for 3 intervals. User-facing text says "base beacon", not Range Test.
- Bench (Mac CLI): the Meshtastic Python CLI needs Python ≤ 3.13 (`uvx --python 3.13 meshtastic --port /dev/cu.usb… --info`). - **MeshCore** (free since 2026-11-05, Andy: no paywall in the connect list; `ProFeature.meshCore` is kept unused so the enum doesn't shift; schema v10; `docs/design/meshcore.md` is the cited protocol reference, 2026-10-29, first session over the air the same day, remaining hardware checks in its §10). `MeshCoreRadio` (`lib/data/radio/meshcore/`: `meshcore_frames.dart` codec, `meshcore_commander.dart` one-command-at-a-time queue, `meshcore_packets.dart` frame → node/packet, `meshcore_presets.dart` snapshot of the MeshCore app's community preset table) speaks the companion protocol v1.18 over the Nordic UART Service through `ble/BleTransport` (now behind the plain-Dart `RadioTransport` interface, faked in `test/meshcore/`). Handshake: DEVICE_QUERY(3) first → APP_START → SET_DEVICE_TIME → GET_CONTACTS → GET_CHANNEL per slot → SYNC_NEXT_MESSAGE drain → ready; GET_STATS every 60 s feeds `channelStats`. Node num = first 4 bytes of the public key (big-endian). Every `0x88` RF-log frame is a `ReceivedPacket` (`type` advert/trace/group/direct/raw; a direct packet with a path has `hopsKnown = false` and is stored as `source_kind = 'log_only'`, excluded from samples like `telemetry_miss`; `SourceKind.notSamples`). **Ping = trace** (`SEND_TRACE_PATH`, flags 2, the base's 4-byte key prefix): `received` carries downlink `snr`/`rssi` plus `uplinkSnr` (`packet_events.uplink_snr`, CSV v2 `uplink_snr`, `PingSample.uplinkSnr`); never `implicit`/`throttled`; the radio consumes its own trace reply (not on `packets`). **Base beacon = `BeaconKind.trace`**, "pulled": the mobile traces the base on the beacon interval and nothing is written to the base (`setBeacon` only echoes). A MeshCore session stores `beacon_kind = 'trace'`, runs the probe at the smaller of the beacon and ping intervals, throws `SessionProbeOffError` when both are off, counts trace timeouts as beacon misses (3 in a row → absent, no timing-synthesized misses), and retunes live via `RadioRoles.beaconChanges`. **Range settings on MeshCore are the ladder** `MeshCoreModulations` (`meshcore_presets.dart`, 2026-10-29): the 10 distinct modulations of the community preset table, fastest link check first, ids `MC_SF7_BW62.5_CR5`… (what `currentPreset`, `sessions.loraPreset` and `RadioRoles` hold; `MeshCoreModulations.ladderId` maps a pre-ladder community id like `MC_USA` onto it so `setupMismatch` and the banner don't flag the base). Community presets (`MeshCorePresets`, frequency + modulation) only name what the radio is on (`regionName`) and decide `onPublicChannel`. Radio Setup shows the ladder ("Range setting", the radio's own tagged "same as your mesh"), the band's relay frequency as a line ("Other…" opens the field) and a TX power stepper. Radio Setup on MeshCore: no reboot, no key exchange, backup first (`MeshCoreBackup`, see Radio backups); `SET_CHANNEL` "MeshTest" with the first 16 key bytes (never slot 0), optional TX power, then `SET_RADIO_PARAMS` with repeat on for the base, which the firmware allows only at 433.000 / 869.495 / 918.000 MHz (else a `StateError` lists them); the UI prefills that slot for the radio's band; base and mobile must share a protocol (`RadioProfileService.sameProtocolMessage`). `onPublicChannel` = params equal a community preset. Airtime floors take `protocol:` (`AirtimeModel.probeAirtimeMsFor`: a trace exchange counts both legs). User-facing text says "link check". MeshCore firmware and the two Dart reference apps are MIT; NOTICE has a "Protocol references" entry, no code copied. Bench: L1 + T1000-E run MeshCore companion 1.18.0; the Heltec V3 is the Meshtastic radio.
